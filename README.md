# TONGTOU 4K — 下落式 4K 音游

一个纯 **HTML + CSS + JavaScript** 的 4 键下落式音游（BMS 风格），目标分辨率 **3840 × 2160**。
使用 `./src` 中提供的音乐，谱面由音频分析离线生成。

**在线玩：<https://yhsome.github.io/TongTou/>** （GitHub Pages，整页只有几 MB，手机上打开也很快）

## ⚠️ 不要直接双击 index.html

直接双击打开会**永远停在「正在初始化…」**。这不是 bug，而是浏览器的安全策略：

```
Access to script at 'file:///.../src/game/main.js' from origin 'null'
has been blocked by CORS policy
```

`file://` 页面的来源是 `null`，浏览器拒绝它加载 ES 模块，所以 `main.js` 一行都不会执行。
（`fetch()`、`decodeAudioData()` 同样被拦截。）

**正确的打开方式 —— 任选一种：**

```
双击 start.cmd           # Windows：自动起服务器 + 打开浏览器
./start.sh               # macOS / Linux

npm start                # 任意平台（= node serve.mjs --open）
node serve.mjs           # → 手动访问 http://127.0.0.1:8080/
python -m http.server 8080
```

页面已内置检测：若你确实用 `file://` 打开了，它会直接告诉你原因并给出可复制的命令，
不会无声卡住。

### 端口被占用怎么办

`serve.mjs` 自己会处理，**不需要你手动改端口**。启动时会探测目标端口上是什么：

| 探测结果 | 行为 |
| --- | --- |
| 空闲 | 正常启动 |
| **本项目、当前版本**（带标识接口 `/__tongtou`） | 复用：「已经在运行」，打开浏览器并退出，不再报 `EADDRINUSE` |
| **本项目、更早启动的服务器进程**（无标识） | 同样复用，并说明它仍在提供最新文件 |
| 别的程序 | 跳过该端口，继续往后找（最多 20 个） |

之所以对「旧服务器进程」也直接复用：`serve.mjs` 每个请求都从磁盘现读文件，
所以**旧的是服务器进程，不是内容**——它给出的仍然是最新代码。

想彻底清掉旧进程：

```
netstat -ano | findstr :8080
taskkill /PID <上面查到的PID> /F
```

测试脚本用 `node serve.mjs <port> --strict` 关掉全部回退逻辑，
以免测试悄悄连到别的端口上。

## 手机端适配

界面按**设备类别**分成两套版式，启动时自动选择（不需要手动指定）：

| | 桌面（BMS 式） | 手机 / 触屏 |
| --- | --- | --- |
| 轨道 | 右侧竖条，占高度的 56% | **全宽四轨**，整个屏幕横向四等分 |
| HUD | 左侧面板（曲名 / 分数 / 血条 / 频谱） | 顶部横条（频谱压在横条里，不占额外高度） |
| 判定线 | 85.5% 高度 | 竖屏 70% / 横屏 78.5% |
| 音效提示 | 判定线下方的 D F J K | 判定线下方的「触控区」色块 |

判断依据是 `(pointer: coarse)` 或短边 ≤ 820px——所以窄窗口的桌面浏览器也会切到全宽版式，
因为 BMS 竖条在那种宽度下本来就不够用。

**触控实现**

* 用 **Pointer Events** 而不是 Touch Events：鼠标、笔、手指走同一条路径，每个触点带独立
  `pointerId`，因此四根手指按四条轨道是四次独立按下/抬起——和弦可以正常打。
* `pointerdown` 时对触点做 `setPointerCapture`，手指滑一点再抬起也仍然算在同一轨道。
* 每条轨道用**计数器**记录当前有几根手指按着，只有最后一根抬起才真正释放。
* 判定区是**整列**（从 HUD 下方一直到屏幕底边），不是判定线附近的一条窄带——
  高速段落里手指落点本来就不精确。按在轨道上方 40% 高度处同样有效（测试里覆盖了这一点）。
* `touch-action: none` + `overscroll-behavior: none`：轻触不会变成滚动、缩放或下拉刷新，
  长按也不会弹菜单。

**其余适配**

* 渲染分辨率按设备分档：桌面预算 3840×2160，手机 240 万像素
  （1080×2340 的机器约 1.35MP），避免在手机 GPU 上硬跑 4K。
* `env(safe-area-inset-*)` 会读进画布：横屏时刘海会压缩轨道宽度，竖屏时把 HUD 横条推下来，
  避免内容被挖孔或圆角吃掉。
* 开局尝试全屏（仅触屏设备，失败静默忽略——iOS Safari 对非 video 元素的 `requestFullscreen`
  会拒绝）。**不锁定方向**：两套版式都能玩，强行转屏很招人烦。
* 旋转屏幕会重算版式（监听 `orientationchange`，延迟 250ms 等尺寸稳定）。
* 菜单控件在 `(pointer: coarse)` 下放大到 44px 以上触控目标，设置项在竖屏下改为单列。
* **左上角暂停按钮**：手机没有 `Esc`，所以对局中有一个 46×46 的暂停键（仅在
  `play` + 全宽版式下出现，桌面端不显示）。它是画布**外的真实 DOM 元素**，
  所以按它绝不会顺带按到轨道；按钮宽度会量出来反馈给渲染器，HUD 的曲名会自动
  让开这一角。

**结算界面必须一页看完**

结算页是唯一一个「出现滚动条就真的在扣玩家东西」的界面：评分、八个计数、
三个操作和一个打赏按钮必须同时看见，否则一定有东西被漏掉。手机上原来的版式是
**724 px 高塞进 393 px 的横屏视口**——355 px 的滚动，打赏按钮直接掉到屏幕外。

所以全宽版式下的结算页不再按「内容」排版，而是按**视口**排版：

| | 桌面 / 长屏 | 全宽版式（手机） |
| --- | --- | --- |
| 头部 | 等级 / 分数 / 准确率 三栏 | 同一行，等级缩到 48–96 px |
| 八个计数 | `auto-fit`，150 px 起的卡片 | **竖屏 4 列 / 横屏 8 列**，纯读数 |
| 操作按钮 | 可换行 | **不换行**，三个等宽一行，`kbd` 提示隐藏 |
| 打赏 | 单独一行 | 单独一行 |

规则全部挂在 `body[data-layout="handheld"]` 上而不是 `(pointer: coarse)` 上——
决定要不要进入「横条 HUD 世界」的是**版式**，不是指针类型（窄窗口的桌面浏览器
也是全宽版式）。另外 320 px 高的横屏（iPhone SE）再额外收紧一档内边距与按钮高度。

实测六种视口，**滚动量全部为 0，且没有任何一处文字被截断**：

```
iPhone 14 Pro 竖 393×852   面板 349 px / 视口 852   ✓
iPhone 14 Pro 横 852×393   面板 268 px / 视口 393   ✓
Pixel 7 竖     412×915     面板 367 px / 视口 915   ✓
iPhone SE 竖   320×568     面板 333 px / 视口 568   ✓
iPhone SE 横   568×320     面板 230 px / 视口 320   ✓（改版前是 333 px）
iPad mini 横   1024×768                            ✓
```

回归测试见 `npm run test:mobile`（100 项）。

## 赞赏（请作者吃包辣条）

结算界面底部多一个琥珀金按钮，点开是微信收款码。做法照抄 `BigNaiWa/sponsor.js`
（连文案也照搬——辣条比矿泉水实在）：

* **纯静态**：没有 `fetch`，没有 `localStorage`，不埋点、不改分数、不影响任何判定。
  弹窗只是「一张图片放在一个盒子里」。
* 触发点只有结算界面——打完了才有资格被打赏，标题页和游戏里都不出现。
* 关闭方式给了四种：右上角 `✕`、底部「关闭」、点灰色背景、按 `Esc` / `Enter`。
  **弹窗打开时独占键盘**：`Esc` 只关弹窗，不会穿透到结算界面的快捷键去把歌重开。
* **`show()` 会自动关掉它**：任何离开结算界面的路径（`R` 重开、`Q` 回标题、选难度）
  都不会把它留在标题页上面。这条曾经很容易漏——键盘快捷键不经过 DOM 点击。
* 手机上换一套尺寸：卡片占满宽度、二维码在竖屏 ≥180px、横屏按 `42vh` 缩放，
  保证**整个卡片不需要滚动**就能看全。手机上还多一行提示：
  「长按二维码保存，或用另一台设备扫」——同一台手机没法扫自己屏幕上的码。

**换成自己的收款码**：把 `assets/sponsor-qr.jpg` 换掉即可（480×480 的方图最合适），
不用改任何代码。不想要这个入口就删掉 `index.html` 里 `#sponsor-btn` 那个按钮，
或整块 `#sponsor-modal`。

## 玩法

| 操作 | 说明 |
| --- | --- |
| 四条轨道键 | 默认 `D` `F` `J` `K`，**可在设置里改成任意键**（含 `A` `S` `K` `L` 预设） |
| 轻触轨道 | 触屏设备：整列都是判定区，支持多指同时 |
| `Space` / `Esc` | 暂停 / 继续 |
| `←` `→` | 暂停时跳转进度（会重置判定） |
| `↑` `↓` | 暂停时微调判定偏移 |
| `R` | 重开本局 |
| `F2` | AUTO 自动演奏（**仅开发者模式**；开着时画面顶部有金色提示，点它也能关） |
| `F9` | 开发者设置（需要口令，见下文） |

### AUTO 不会粘住，而且锁在开发者模式后面

AUTO 是**开发者工具，不是玩家功能**。两条规矩叠在一起：

1. **没解锁开发者模式就用不了**——`F2`、`setAutoPlay(true)`、开发者界面里的开关，
   在锁着的时候都会被拒绝（提示「自动演奏只在开发者模式下可用」）。
   **退出开发者模式会顺手把 AUTO 关掉**：它不能活得比解锁它的那个模式更久。
2. **它也不写进 localStorage**——`config.js` 里 `autoPlay` 在 `EPHEMERAL` 集合中，
   `saveSettings()` 不写、`loadSettings()` 不读。旧版本留下的 `autoPlay: true` 一并被忽略。

第 2 条是被用户骂出来的：早先它会跟着设置一起持久化，于是**一次误按 F2 就让游戏从此每局都自己打**，
屏幕上没有任何提示，唯一的出口是一个没人知道的 F2。当时的提示还是 `autoPlay: 开`，
连提示本身都看不懂。

开着的时候：

* **屏幕上看得见**——画面顶部中央有一枚金色 `AUTO · 点击关闭` 指示条，
  它是画布外的真实 DOM 元素（不会误触轨道），**点一下就关**。
* **手机也能关**——手机没有 F2，这枚指示条是唯一的出口；触屏下它自动放大到 40px 高。
* 关掉时提示读作「已关闭自动演奏」，而不是内部的 `autoPlay` 键名。

### 设置只有六项

这是一款小游戏，所以**设置界面刻意保持很短**：

```
轨道键位 · 下落速度 · 判定偏移 · 音量 · 打击音效 · 演出特效
```

一条判据：**只有真正因人而异的选项才配占一个设置项**——你的键位、你读谱的速度、
你的音频偏移、你的音量、以及你要不要音效和演出。

其余全部是 `config.js` 里的常量，选好一个值就固定下来：

| 曾经是设置项 | 现在的处理 |
| --- | --- |
| 屏幕停留时间 | 与「下落速度」是同一件事，合并成一个滑条 |
| 整体压暗 / 频谱可视化 / 键位提示 | 常量，默认开 |
| 打击反馈强度 | 常量「强烈」 |
| 打击音效音量 | 跟随主音量（× 0.7），不再单独一条 |
| 显示实时判定偏差 | **拖动「判定偏移」时自动出现 4 秒**，平时不占位 |
| 渲染分辨率 | `auto` 已经是「桌面 4K / 手机 2.4MP」的良好默认 |
| 界面布局 | 按设备自动判断 |
| 开局全屏 | **默认关**——以前会在有触摸屏的设备上抢全屏，普通触屏笔记本也算，一个背景小游戏没道理占掉整个屏幕 |

### 改默认值为什么还需要「迁移」

上表里那些常量只要翻一下 `DEFAULTS` 就生效了——**除非玩家已经存过设置**。存档时写的是
**整个** settings 对象，所以读回来时**存的值永远压过新的默认值**，改默认只对从没用过设置界面的人有效。
「开局不要自动全屏」如果只翻 `DEFAULTS`，在你这台机器上会**静默失效**。

所以 `config.js` 里有一张迁移表：

```js
const SETTINGS_REV = 1;
const MIGRATIONS = [
  // rev 0 -> 1: 跑一次就抢全屏，而有触摸屏的设备包括一堆普通笔记本
  (s) => { s.fullscreenOnStart = false; },
];
```

存档里带一个 `rev`：没有 `rev` 的旧存档（rev 0）会被迁移到当前版本，迁移完打上 `rev: 1`。
**迁移只跑一次**——迁移之后你手动打开「开局全屏」，那就是你的选择，会被正常保存下来。
这两条都有断言（`an old blob carrying the previous default is migrated` /
`a deliberate choice made after the migration is kept`）。
| 练习模式 / AUTO | 常量（练习默认开；AUTO 锁在开发者模式后面，且不持久化） |

浏览器测试里有一条断言盯着这个列表（`≤ 6 行`，且不得出现「渲染 / 布局 / 全屏 / AUTO / 练习」
之类的字眼），所以它不会慢慢又长回去。

### 开发者模式

「从设置里拿掉」不等于「删掉」——上面那些常量总得有人能改。它们现在都在**开发者设置**里，
用同一套控件、同一个 `settings` 对象、同一条生效路径。

**怎么进**：`F9`，或者在设置界面点「开发者设置」。两者都只**弹出**口令框，不会直接放行。

```
口令：114514
```

> 说清楚这是什么：整个游戏都在浏览器里跑，能打开控制台的人就能从 `config.js` 里读到
> `DEV_PASSWORD`。它是一个**门槛，不是安全边界**——用来挡住闲着乱点菜单的玩家，
> 不是用来挡有心人的。这个弹窗自己也把这句话写在上面了。

解锁一次就记住了（存在自己的键 `tongtou.dev.v1` 上），所以开发者不用每次刷新都重打。
`?dev=1` 的语义也改成了「打开页面时自动弹出这个口令框」，**不能绕过口令**——
否则这道门在字面上就没意义了。

**里面有什么**（14 项，按画面 / 手感 / 音声 / 调试分组）：

| 分组 | 项目 |
| --- | --- |
| 画面 | 渲染分辨率、界面布局、整体压暗、频谱可视化、键位提示、开局全屏（默认关） |
| 手感 | 下落时长、打击反馈（关 / 普通 / 强烈）、实时判定偏差、练习模式 |
| 音声 | 打击音效音量（原来硬编码 ×0.7，现在是 `hitGain`） |
| 调试 | 自动演奏（AUTO） |

几个刻意的设计：

* **AUTO 关在门后面**：自动演奏是开发者工具，不是玩家功能。没解锁时 `F2` 和
  `setAutoPlay(true)` 都会被拒绝（提示「自动演奏只在开发者模式下可用」），
  **退出开发者模式也会顺手把 AUTO 关掉**——它不能活得比解锁它的那个模式更久。
* **不污染玩家设置**：开发者模式的开关存在自己的键上，而不是塞进 settings ——
  所以「恢复默认」不会把开发者界面收走，开关开发者模式也不会重写玩家的设置。
  测试里两条都断言了。
* **入口永远在，口令才是门**：设置界面那颗「开发者设置」按钮**一直可见**。
  它只负责弹出口令框，本身不解锁任何东西，所以藏起来既没换来安全，又换走了可达性——
  手机没有 `F9`，按钮一藏，触屏设备上开发者界面就彻底进不去了（这个坑是被用户指出来的）。
  现在手机端有 7 条断言盯着它：可见、≥40px、在视口内不用滚动、点开是口令框而不是界面本身。
* **运行中按 F9 不会把跑着的歌晾在那儿**：会先暂停，退出开发者界面时回到**暂停菜单**
  （`devReturnTo` 记住来路），而不是回到设置界面把一局暂停的歌丢在后面。
* **改动立即生效**：改「打击反馈」直接落到 `renderer.fxLevel`，改「渲染分辨率 / 界面布局」
  立刻重建渲染目标——走的是和玩家设置完全一样的 `applySettingsToLive()`。
* **列表自己滚，界面不滚**：14 项不可能在每种视口里都塞下，所以标题和三个按钮固定，
  中间的列表内部滚动。`#dev` 用 `grid-template-rows: minmax(0, 1fr)` 让面板的
  `max-height: 100%` 有个真实的参照物，界面本身始终 `scrollHeight == clientHeight`。
* 帮助界面里也写了 `F9`，否则这个入口只有读源码的人知道。

### 键位绑定

`设置 → 轨道键位`：点任意一个方框，然后**按下你想用的键**即可，`Esc` 取消。

* 内置预设：`DFJK`（默认）、**`ASKL`**、`ASDF`、`JKL;`、`1234`、小键盘 `1245`
* **按到已占用的键会交换两条轨道**，而不是报错——玩家意图很明确
* 系统功能键（`Esc` / `Enter` / 方向键 / `F1`–`F12` / 修饰键）不可绑定，按下会提示换一个
* 绑定写入 `localStorage`；游戏内的键位提示、帮助页、标题页都会同步更新
* 对局中**绑定键优先于全局快捷键**：即使把某条轨道绑到 `Space` 或 `R`，它依然属于那条轨道

键值存的是 `KeyboardEvent.code`（物理键位），所以换成俄语、德语等布局时按键位置不变。

**判定窗口**

| 判定 | 窗口 | 分值 |
| --- | --- | --- |
| PERFECT | ±22 ms | 2.0 |
| GREAT | ±45 ms | 1.0 |
| GOOD | ±80 ms | 0.5 |
| BAD | ±130 ms | 0 |
| MISS | 超出窗口 | 断连 |

### 打击音效

每次成功判定会播一声**清脆的「嗒」**：2.5 ms 噪声瞬时起音 + 两个快速衰减的高频分音
（1980 / 2970 Hz，相差五度）+ 一点 640 Hz 的低频body。

* 音色是**离线合成一次的 PCM**（85 ms），播放时只 `start()` 一个 BufferSource，
  不再每次命中都创建振荡器——音游每秒会触发好几次，播放路径必须零分配。
* **按轨道变调**（1.0 / 1.122 / 1.335 / 1.498，接近小三和弦），所以四键齐按听起来是和弦
  而不是四声一样的咔哒。
* 音量随判定递减：PERFECT 100% / GREAT 85% / GOOD 60% / BAD 35% / MISS 无声。
* `设置 → 打击音效` 可开关（音量跟随主音量，不单独占一个滑条）；音效**直连输出**，
  不经过频谱分析节点，避免被 FFT 窗口拖慢。

**计分：基础分 + 理论值**

满分**不再固定为 1,000,000**，而是按谱面推导：`音符数 × (100 + 50)`。

| 判定 | 基础分 |
| --- | --- |
| PERFECT | 100 |
| GREAT | 50 |
| GOOD | 25 |
| BAD / MISS | 0 |

**理论值**：命中 PERFECT 时，除基础分之外再拿

```
理论值 = 50 - |玩家按键时刻 - 理论最佳时刻| 的毫秒数
```

* 分毫不差 = **+50**；踩在 PERFECT 窗口边缘（22 ms）= **+28**。
* 常数 50 必须大于 PERFECT 窗口（±22 ms），否则理论值会变成负数。
* 只有 PERFECT 有理论值，GREAT / GOOD 不参与。
* 因此单音符最高 100 + 50 = 150 分；`hard`（421 音符）满分 **63,150**，
  `extra`（659 音符，含和弦）满分 **98,850**。
* 结算界面的「理论值 xx%」就是 `本次理论值总和 / 该谱面理论值上限`。

**准确率与计分分离**：`ACCURACY` 只由基础分权重决定（沿用 BMS 口径——全 GREAT = 50%、
全 GOOD = 25%），不受理论值影响。这样评级（AAA ≥ 98.1%…）衡量的是**判定质量**，
而分数额外奖励**精度**。所以「全 PERFECT 但都偏 20 ms」= 100% 准确率，但拿不到满分。

**血条**：起始 20，每命中/失误按 `100/总音符数` 为单位增减；归零即失败（练习模式除外）。

### 打击反馈

**成功的判定会把音符立刻吃掉**（不再是钉在判定线上淡出），并在原处炸开一组分层特效：

| 层 | 表现 |
| --- | --- |
| `core` | 判定线上横跨整条轨道的白色椭圆爆闪 + 一条亮切线 |
| `wave` | 从判定线向外扩散的冲击波轮廓 |
| `beam` | 沿轨道向上冲的光柱 |
| `flash` | 整条轨道底色被该轨颜色浸染 |
| `spark` | 带重力的粒子，**随机错峰 0~60ms** 射出（不是同一帧齐发） |

全部用 `lighter` 叠加混合，重叠处自然变亮。同时受体在命中瞬间**放大外扩**
（`1 + 0.55×`），让按键有"被顶到"的手感。

强度随判定递减：PERFECT 24 粒 / GREAT 15 / GOOD 8 / BAD 4；MISS 只有一次红色警示闪烁、无粒子。
反馈强度是内部常量（默认「强烈」），不占用设置项。

性能上有硬上限（600 个活跃特效）与到期回收：实测 4K 下 600 个特效同时在场时
单帧绘制约 1.5ms（1080p 量级），仍远在 16.7ms 预算内。

### 演出特效（爆火 / 金色边框）

谱面可以在指定位置放演出特效，持续 3.5 秒，**整幅画面由冷转暖，屏幕边框变成金色**。

| | 表现 |
| --- | --- |
| 边框 | 三条递减宽度的金色描边 + 四角圆弧加亮（不用 `shadowBlur`，太贵） |
| 光晕 | 从四条边向内渗透的暖色渐变带（0.10 × 屏高） |
| 微粒 | 54 颗缓慢明灭的金色微尘，**只出现在边框带里**，绝不进入轨道区 |
| 调色 | `#grade` 覆盖层（opacity + sepia/hue-rotate）+ 画布暖色冲淡，两层一起把整个画面染暖 |
| 开销 | 峰值约 **+11 次填充 / +7 次描边 / +4 次矩形** |

边框会**避开刘海与小白条**（四边各按 `safe-area-inset` 内缩），桌面端与手机端共用同一套
表现——**屏幕中间完全不被遮挡**，音符始终清晰可读。

> 早先桌面端是一排火焰柱（15 根火柱 + 26 团烟 + 420 颗火星，峰值 404 次绘制），
> 已经**整段删掉**。理由：任何帧率下它看起来都更像一张贴图，而不是火；真正卖住那个瞬间的
> 是整屏冷→暖的调色，那部分一点没动。删掉之后峰值绘制从 404 降到约 90。

`设置 → 演出特效` 可关闭。

**触发时机是「音符抵达判定线的那一刻」**——即 `note.time`，不是音符在屏幕顶端生成的
时候（两者相差一个下落时长，默认 0.82 s）。特效由时钟驱动、不经过判定系统，
所以**没打到那个音符，特效照样放**。

**默认按音频能量自动挑高潮段**：

```
# tools/analyze.py
FIRE_AUTO         = True    # 自动模式
FIRE_AUTO_COUNT   = 10      # 挑几个
FIRE_AUTO_SPREAD  = True    # 把全曲等分，每段各取自己的峰值
FIRE_AUTO_MIN_GAP = 11.0    # 段内去重的最小间隔
FIRE_AUTO_SKIP    = 8.0     # 前奏不放
```

判据不是「某一瞬间很响」，而是**持续响 + 音符密集**：把响度平滑成约 1.5 秒的
「段落能量」曲线，再和 2 秒窗口内的起音密度加权。

`SPREAD` 是关键——**全局取前 N 名永远只会落在最响的那段副歌里**，前半段一个都轮不到。
改成把全曲等分成 N 段、每段各取峰值，前后半就都有火：

```
  hard    8 bursts  *@17.52s *@29.37s *@45.67s *@60.48s *@73.81s *@87.52s *@113.81s *@132.33s
  expert  8 bursts  *@17.52s *@29.37s *@45.67s *@60.48s *@73.81s *@87.52s *@114.00s *@132.33s
  extra   8 bursts  (与 expert 相同——和弦不改变音符时刻)
```

前半段（17.5 / 29.4 / 45.7 s）的能量确实比后半段低（0.62–0.71 vs 0.89–1.00），
但每段取的都是**该段自己最响的那一刻**。

**也想手写位置**就关掉 `FIRE_AUTO`，用下面任意一种（时间更稳）：

```python
FIRE_CUES      = {"hard": [133, 168, 240, 318, 350]}   # 1-based 音符序号
FIRE_CUE_TIMES = {"hard": [38.26, 48.63, 68.63]}       # 秒；非空时优先
```

> ⚠️ 序号**很脆**：重新生成谱面会让某个位置之后的每个序号都平移，从而**静默地把 cue
> 指到别的音乐位置**（这个坑真踩过）。记位置请优先用秒。

**每个难度各存一份 cue，且必须落在该难度真实存在的音符上。** 这点也踩过坑：最初我把
「困难」的 cue 列表共享给所有难度，结果在某个难度上特效会在**离最近音符 19.7 秒**的
地方炸开。现在会把每个 cue 吸附到各难度自己的最近音符（自动模式允许 1.2 s——高潮是
持续几秒的段落；手写序号则要求精确命中）。

#### 怎么让它看起来「自然」

第一版很突兀，原因是起爆太硬（0.14 s 冲到满）。现在整条包络走 `smoothstep`，实测
`u=0→1` 的强度是 `0.00 0.19 0.58 0.93 1.00 …1.00 0.97 0.84 0.66 0.46 0.26 0.10 0.00`
——缓起、长持、缓落。这条曲线本身也是断言的一部分，不靠肉眼判断。

另外两点也在同一时期改掉，之后一直保留：闪烁从 34 Hz 降到 2.3 / 5.7 两层慢波叠加
（快频看起来像频闪）；边框整体做缓慢呼吸，像是被"点亮"而不是"被打开"。

**整屏冷→暖调色**是三层叠出来的：`<video>` 的 CSS filter 做 sepia/hue-rotate，
`#grade` 覆盖层做暖色 screen 混合与 sepia/hue-rotate，画布再做一层暖色冲淡——两层合起来整个画面一起变色。

实现上**完全由时间驱动，没有任何粒子状态**：每一颗微尘的位置都由 `(事件序号, 粒子序号)`
哈希 + 当前时间算出。因此暂停、跳转、掉帧都不会让特效漂移或残留，两次爆发之间也不可能
互相污染。绘制只有一遍，在轨道**之后**画，但因为全部落在边框带里，音符依然清晰可读。

`设置 → 演出特效` 可关闭。

```
npm run test:browser        # 专测演出特效（含包络曲线、边框描边、调色断言）：锁定音符、触发时刻、3.5s 后停止、开关、开销
node tools/probe-fire.mjs   # 实机验证：真实跑一遍 hard，看特效出现时音符是否在判定线上
```

## 谱面是怎么来的

`tools/analyze.py` 从音频里生成 `src/chart/雨爱.json`。核心难点是**同时**拿到稳定的
节拍网格和锐利的起音时刻——单一检测器做不到：

* 检测器越宽松，混响、气声、弓弦噪声带来的「伪起音」越多，这些点大多不在网格上；
* 检测器越严格，时刻越准但音符太少。

于是用**两层**结构，并用复相位集中度作为客观指标筛选：

```
                                        音符数   |z|    中位偏差
log 通量 + HPSS + z-score 白化             745   0.49     62.6 ms
log 通量（细跳步）+ 中值/MAD 阈值           671   0.27     66.6 ms
线性功率通量（细跳步）+ 严格阈值            403   0.66     13.3 ms   ← 打击层
线性功率通量（最严格）                      221   0.87      7.8 ms
```

其中 `|z| = |mean(exp(2πi·t/P))|`：所有起音都精确落在网格上时为 1，完全随机时趋近 0。

最终方案：

1. **打击层** — 线性功率谱正通量，严格阈值 → 时刻准确（中位 13 ms）的核心音符；
2. **旋律层** — 400–3500 Hz 对数通量 → 补足音符密度；
3. 两层**吸附到 1/16 网格**。这一步之所以安全，正是因为打击层的时刻误差
   （13 ms）远小于半个网格（162 BPM 下为 46 ms）；
4. 轨道分配用**百分位秩**而非绝对阈值——低音/重音走外侧键（D、K），旋律走内侧键（F、J），
   因此无论频谱分布如何，四键都保持均衡。

结果：`162.000 BPM`（候选 162.5 的 |z| 骤降到 0.06，说明该速度极其确定），谱面覆盖 0–139 s。

**相位精修与旋律层收紧**（v2）

用 `tools/chart-check.py` 量化后修掉了两个问题：

1. `pick_grid` 最大化的是 |z|，也就是起音时刻的**圆周均值**；而真实起音是「陡升缓降」的
   不对称波形，均值会比听感上的击点晚几毫秒。新增 `refine_phase()` 在 ±55 ms（小于一个
   16 分音符，不会跳到相邻格）内搜索让**拍点能量最大**的相位。实测移了 **+13.0 ms**，
   打击层吸附误差从 **13.0 ms 降到 3.8 ms**。
2. 旋律层检测器远比打击层宽松（±40 ms），把它的起音全部强行量化，等于凭空造出
   距任何声音最远半格的音符。现在只保留**本来就落在网格 26 ms 内**的起音，603 个里
   丢掉 216 个。专家难度「距真实起音 ±25 ms 内」的比例从 **53.5% → 71.3%**。

量化对比：

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 整体偏移 | +12 ms | **0 ms** |
| hard ±25 ms 命中率 | 68.5% | **90.6%** |
| expert ±25 ms 命中率 | 53.5% | **71.3%** |
| 打击层吸附误差（中位） | 13.0 ms | **3.8 ms** |
| hard 落在 1/16 上 | — | **100%** |
| extra 落在 1/16 上 | — | **100%** |

同时改了**轨道分配**：原先「打击层走外侧键、旋律层走内侧键」，在旋律层被削掉之后
中间两键几乎空了（某一难度变成 `[128, 0, 2, 106]`）。现在由**频谱质心的百分位秩**决定轨道
（`round(rank*3)` 给出 17/33/33/17 的分布），低音重击才额外指定外侧键，因此无论两层
各贡献多少，四键都保持在使用中（expert `[60, 164, 162, 106]`）。

**难度分层：全局阈值 + 局部阈值 + 和弦（v4）**

> 历史：早期有 `easy / normal / hard / expert` 四档。`easy` 和 `normal` 后来被删掉了
> （下一节就是原因），现在只有 **`hard / expert / extra`** 三档。

一个全局强度阈值在这首歌上会把后半段整段丢掉：

```python
thr = 全曲强度排序后第 (总数 × ratio) 名        # 一个全局阈值
```

问题出在这首歌**不在同一把尺子上**：后半段整体更响，但更连奏（长音、弦乐、和声），
起音反而更钝，所以它的强度**全曲排名系统性偏低**。被删掉的 `easy`（ratio 0.22）当年是这样：

| 每 10 秒音符数 | 0-10 | … | 90-100 | 100-110 | 110-120 | 120-130 | 130-140 | 总计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `easy`（全局阈值） | 18 | … | 4 | **0** | **0** | **0** | 1 | 108 |
| `easy`（双阈值） | 18 | … | 13 | **15** | **18** | **17** | 12 | 197 |

前 50 秒 78 个音符、后 40 秒 4 个——那不是难度分层，那是断崖。

现在每个难度拿**两个阈值，过一个就留下**：

* **全局阈值**（原来的那套）——决定这个难度本来就打得好的部分；
* **局部阈值**——在**自己的 8 秒窗口内**（约 5 小节）取同样的分位。

局部阈值只能把门槛**降低**，所以这条规则是**只加不减**：原本排在谱面上的音符一个都不会消失，
稀疏的窗口被补到它应得的份量，其余原样保留。`local_ratios` 略高于 `ratios`
（0.82 / 1.0），因为安静的段落也应该有东西可打。

**`extra` 不是「检测出更多音符」**：`expert` 的 ratio 已经是 1.0，占满了全部 492 个候选格，
上游没有东西可挖了。真正的顶级难度也不是靠塞更多音符变难的——而是靠**把手上的重音变成双手**
（和弦）。所以：

```python
EXTRA_CHORD_RATIO = 0.34    # 最强的 34% 音符各配一个同刻的伙伴轨
```

伙伴轨优先取**镜像轨**（0↔3、1↔2），让两只手分摊而不是让一只手打双押；只从那一刻
**空着**的轨道里选，且同一个 tick 最多两个音符。结果是 492 + 167 = **659 音符（4.71 NPS）**，
四象限 `196 / 157 / 153 / 153`。

顺带一提，`extra` 的**对音质量反而最好**：对齐分数 0.4658（expert 0.4064），
±25 ms 内 100% 覆盖强起音，1/16 量化 100%——因为和弦只加在最强的那些起音上。

（`bar[i] = min(全局门槛, 局部门槛)`，所以原本过得了全局门槛的音符必然仍然过得了。）

三个难度的四个象限分布：

| 难度 | 音符数 | NPS | 四个象限 |
| --- | --- | --- | --- |
| hard | 421 | 3.01 | 102 / 95 / 100 / 124 |
| expert | 492 | 3.51 | 121 / 103 / 118 / 150 |
| extra | 659 | **4.71** | 196 / 157 / 153 / 153 |

（作为对照，那个被删掉的 `easy` 在修好双阈值后是 197 音符 / 1.41 NPS，
象限 62 / 38 / 42 / 55——不再是 77/60/37/**3**。）

`offset`、`tick`、`bpm`、`duration` 一个字节都没动，只有音符的选择变了。音质也没有因为
变密而变差：hard 有 **90.6 %**、extra 的强起音 **100 %** 被覆盖，两者 1/16 量化都是
**100 %**，整体偏移 **0 ms**。

`npm test` 里有一组断言把这个形状钉住：**任意一个象限的音符数不得低于平均值的 45 %，
且最薄的象限不得少于 30 个音符**；此外还检查**同一 tick 最多两个音符**（和弦可以，
三押墙不行）、**同轨最小间距 ≥ 90 ms**、**难度密度必须严格递增**。
把旧的全局阈值谱面放回去，这些断言会立刻失败。

**开局的幽灵音符**（v3）

曾经在 0.018 s 出现过一个音符（tick 为负）。两个原因叠在一起：

1. 音频是**淡入**的，而 `log1p()` 是动态压缩——淡入期间把「近乎无声 → 很小」放大成了巨大的
   *相对*跳变，旋律层的通量在开头冲到 58，比真实起音的中位数 35.6 还高，被当成一个起音。
2. 没有引导时间，任何落在开头的音符在播放开始的瞬间就已经错过了判定窗口。

修法：

* 旋律层加上**绝对能量闸门**（低于响帧 99 分位的 5% 的通量一律归零），淡入/静音段不再产生起音；
* 谱面加入 `LEAD_IN = 1.0 s`，并额外保证不出现负数 tick；
* `chart.js`（浏览器内自动谱面）同样加了闸门与引导时间；
* 引擎侧再加一道保险：**开局时已经超出判定窗口的音符会被标记为 `skip` 并移出计分分母**，
  既不判 MISS 也不断连、也不压低满分——这样任何来源的谱面都不会因为开头的野音符白扣一分。

```
python tools/analyze.py                 # 重新生成（需要 numpy）
python tools/analyze.py --keep-wav      # 保留中间产物
python tools/chart-check.py             # 对照音频体检现有谱面（偏移/命中率/节拍落点）
```

依赖 `numpy`，ffmpeg 会自动使用 `imageio-ffmpeg` 自带的二进制。
音频路径、曲名、艺术家在脚本顶部的 `TRACK` 字典里修改。

## 4K 相关

* Canvas 后备缓冲独立于 CSS 像素。分辨率档位**自动选择**（不再占用设置项）：
  桌面按 DPR 上探到 **3840×2160** 的像素预算，手机限制在约 240 万像素。
  需要强制指定时改 `config.js` 的 `DEFAULTS.renderScale`
  （可选 `1080` / `1440` / `2160` / `4320`）。
  所有版式数值都以渲染目标尺寸的比例表达，
  因此 1080p 与 4K 的构图完全一致，只是像素密度不同。
* 实测：headless Edge 在 **3840×2160 下稳定 165 FPS**（软件光栅）。
  静态轨道底图与音符图元预先烘焙到离屏 Canvas，每帧只做 `drawImage`。
* 每条轨道的键位提示位置由「判定线到轨道底部」这段可用空间推导，
  不会在窗口比例变化时与进度条重叠。

## 时序实现要点

音游对时钟很敏感，这里做了三件事：

1. **以 Web Audio 采样时钟为准**（`AudioContext.currentTime`），不用
   `HTMLMediaElement.currentTime`——后者不单调且精度差。
2. **输入亚帧打点**：按键事件的 `event.timeStamp` 与音频时钟通过每帧校准的
   `(performance.now, audioTime)` 映射换算，取回事件真实发生时刻，
   而不是把它量化到渲染帧（60 FPS 下相当于 ±8 ms 的随机误差）。
3. **延迟补偿**：`audio.now()` 会减去 `outputLatency`（回退到 `baseLatency`），
   判定对齐的是玩家**听到**的声音。

### 一个容易踩的坑：`await ctx.resume()`

浏览器创建的 `AudioContext` 默认是 `suspended`，而 **`resume()` 返回的 Promise 在页面获得
用户激活之前永远不会 settle**。所以启动流程里任何一处 `await ctx.resume()` 都会永久卡住。

本项目的做法：

* `init()` 只负责建图和**从不** `await resume()` —— `decodeAudioData()` 在 suspended
  状态下是合法的，所以启动可以在玩家交互之前完成；
* 音频真正的启动交给 `ensureRunning()`，它在真实手势里调用，并用超时兜底；
* 播放开始前会确认 context 确实处于 `running`。这不只是「有没有声音」的问题：
  suspended 时 `ctx.currentTime` 不前进，`now()` 会冻结，整个谱面会静止不动。

`tools/boot-probe.mjs` 专门覆盖这条路径，注意它**不能**加
`--autoplay-policy=no-user-gesture-required`（那会让 context 一开始就是 running，
把这个 bug 藏起来），并且必须用 CDP 的可信输入——`Runtime.evaluate` 里合成的
`KeyboardEvent` 不带用户激活，永远无法解锁音频。

## 已知限制

* 自动谱面是**音频分析的产物**，不是人工编排；节奏型与轨道分配未必符合人工意图，
  击打声部与旋律声部会被区分对待，但装饰音可能被写入或漏掉。
* **没有 BGA 了**：原来有一段 1920×1080 的翻唱版 MV 垫在谱面后面，但它有 69 MB，
  占了整页体积的 91%，而且画面在轨道底下相当吵。删掉之后只剩渐变色 + 暗角，
  音符反而清楚了很多。想加回来：把视频放回 `src/`，在 `<div id="stage">` 里放一个
  `<video>`，再让 `applyFireGrade()` 顺手给它的 `filter` 赋值即可。
* 音频是翻唱版，因此谱面里的艺术家字段标为「翻唱版」以免误导；可在 `tools/analyze.py`
  的 `TRACK` 中修改。
* 判定偏移是全局设置，不按曲目分别保存。
* 暂停后跳转进度会重置本局判定记录，这是刻意的——引擎按音符保存状态，
  中途跳转无法合理折算。
